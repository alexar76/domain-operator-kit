# Запуск и эксплуатация

## Три режима

| Режим | Регистратор | Платежи | Назначение |
|---|---|---|---|
| `demo` | Встроенная симуляция | Симуляция | Демо и тесты |
| `sandbox` | Sandbox Openprovider или HTTP-поставщика | Симуляция | Проверка аккаунта и фактических API |
| `live` | Production-поставщик | USDC Base, CDP facilitator | Реальные продажи после проверки |

Live-режим отвергает demo-провайдера и demo-платежи. Обратная комбинация — реальные платежи с sandbox-регистратором — также запрещена. Тестовые котировки явно помечены. Не используйте production-аккаунт за HTTP bridge, объявленным как sandbox.

## Первый оператор

1. Создайте отдельный sandbox-аккаунт Openprovider, включите API и сохраните его логин/пароль в файлах с правами `0600`. Используйте `.env.example`, `DOMAIN_MODE=sandbox`, `DOMAIN_PROVIDER=openprovider`.
2. Проверьте котировку, создание контакта, регистрацию одного тестового домена, DNS, продление, сверку после потерянного ответа. Проверьте фактические статусы email, цены/валюту и создание DNS-зоны в вашем аккаунте. Адрес sandbox отличается от production.
3. Для production задайте HTTPS `DOMAIN_PUBLIC_URL`, идентификатор и название продавца, опубликованные условия и их версию. Подключите production-аккаунт регистратора и доступные ему TLD.
4. Убедитесь, что выдаваемая API закупочная цена включает затраты оператора. `DOMAIN_UPSTREAM_COST_CONFIRMED=1` — явная отметка этой проверки. Код не рассчитывает налоговый режим продавца. Разницу при изменении обычной цены между проверкой и регистрацией Openprovider несёт оператор.
5. Настройте `PAY_TO` — адрес получения USDC в Base, `CDP_KEY_FILE` — JSON `{id,privateKey}` для CDP API, `DOMAIN_REFUND_KEY_FILE` — hex-ключ выделенного кошелька возвратов. Его USDC-баланс должен покрывать возвраты; входящие оплаты сами по себе не пополняют отдельный резерв. RPC должен поддерживать finalized-блоки и нужные исторические логи.
6. Задайте максимальный возврат и дневной бюджет, достаточные для предлагаемых доменов. Слишком дорогие заказы могут остаться `refund_due` до увеличения лимита. Обеспечьте поддержку владельцев, уведомления об окончании срока и доступ к регистратору.
7. Выполните контролируемую реальную проверку с доменом, который вы действительно намерены приобрести, и разрешённым бюджетом. Локальные тесты этого шага не заменяют.

Существующие рабочие аккаунты, кошельки, деплои и реальные домены в ходе разработки не использовались.

## Размещение

Нужен постоянный Node-процесс и надёжный локальный диск для SQLite. `data/` нельзя заменять пустым каталогом при каждом деплое. Vercel используется для сайтов покупателей; этот сервер не рассчитан на эфемерные serverless-инстансы.

```sh
cp .env.example .env
# Заполните .env выбранным режимом.
docker compose up --build -d
```

Compose публикует порт только на loopback. Внешний HTTPS проксируется вашим существующим ingress/nginx; пример — [deploy/nginx.conf.example](deploy/nginx.conf.example). Секретные файлы для live подключите отдельными read-only mounts или Docker secrets, а пути задайте через переменные `*_FILE`. Они не включаются в образ. Процесс контейнера работает пользователем `node`; обеспечьте ему чтение секретов и запись в volume. Пример compose без этих mounts предназначен для demo.

Запускайте **одну реплику на одну базу**. PID-lock обнаруживает второй процесс; Linux также проверяет идентичность запуска процесса, чтобы не спутать повторно использованный PID после рестарта контейнера. На других системах повторное использование PID может потребовать ручной проверки stale-lock. Удалять `server.lock` допустимо только после подтверждения, что ни один продавец не использует базу.

Сервис подписывает URL, заданный в `DOMAIN_PUBLIC_URL`. Прокси не должен менять его публичную схему/путь. Автоматические повторные POST на уровне прокси выключите. Встроенный лимит — 120 запросов/минуту на TCP peer; за одним прокси он будет общим. Для большой нагрузки настройте лимиты на ingress и пересмотрите конфигурацию сервера, не доверяя произвольному `X-Forwarded-For`.

## Федерация AIMarket

Сервис предоставляет `listing.json`, а существующий `aimarket node` публикует стандартный federation manifest. Это тот же механизм узла, что используется другими операторами; kit не придумывает альтернативный manifest.

```sh
node bin/domain-rails.mjs node-toml \
  https://domains.seller.example \
  https://node.seller.example \
  http://127.0.0.1:9495 > node.toml
```

Затем используйте обычный процесс запуска и регистрации `aimarket node` из [документации AIMarket](https://github.com/alexar76/aicom). Federation wrapper устанавливается отдельно и не включён в этот репозиторий. Конфигурация публикует только `domains.quote@v1`; цена вызова котировки нулевая. Ответ содержит прямой `order_url`. Private capabilities присутствуют в каталоге продавца, но не должны проксироваться Hub. Не публикуйте demo-узел как production-продавца.

## Наблюдение

`/healthz` возвращает режим, тип поставщика, публичный ключ и число незавершённых заказов. Это проверка живого процесса, не готовности денег/регистратора. Следите за ростом pending, возрастом заказов, резервом возвратов и истечением доменов; автоматические оповещения и renewal scheduler в v1 не входят.

Подробный отчёт доступен локально после остановки сервера:

```sh
node --env-file=.env bin/operator.mjs report
```

Отчёт содержит ID, домен, состояние, цену и транзакции без контактов и авторизаций. В базе есть зашифрованный аудит переходов. HTTP-ошибки намеренно не содержат исходные сообщения регистратора: они могут включать персональные данные.

## Восстановление

| Состояние | Что делает система | Действие оператора |
|---|---|---|
| `settlement_pending` | Проверяет исходную авторизацию в finalized Base-логах | Восстановить RPC/CDP, не отправлять новое списание |
| `paid` | Продолжает подготовку | Восстановить доступ к поставщику |
| `preparing` после рестарта | Через 120 с переводит к возврату: регистрация ещё не запускалась | Возможен лишний неоплачиваемый contact handle |
| `registration_pending` | Только сверяет результат, не повторяет submit | Проверить конкретную операцию в аккаунте регистратора |
| `refund_due` | Пытается подготовить возврат в пределах лимитов | Проверить резерв, ключ, CDP и лимиты |
| `refund_preparing` после рестарта | Освобождает неиспользованную резервацию, готовит заново | Settlement ещё не вызывался |
| `refund_pending` | Проверяет исходную авторизацию возврата | Не подписывать второй возврат |
| `refund_review` | Останавливает автоматический возврат | Разобрать доказанно неиспользованную авторизацию; автоматическая замена не реализована |

Отсутствие домена в поиске или тайм-аут не доказывают отказ. Возврат за домен, который всё-таки зарегистрировался, создаёт финансовую ошибку. Регистрация и платёж не являются единой атомарной транзакцией.

Для Openprovider неизвестный ответ на продление требует подтверждения именно этой операции. После проверки журнала регистратора можно записать **ручное свидетельство администратора**. Это не криптографическое доказательство и не способ обойти проверку.

1. Остановите сервис и сделайте согласованную резервную копию.
2. Получите подтверждение регистратора и его ссылку/ID; проверьте, что операция не может завершиться позднее.
3. Создайте приватный JSON:

```json
{
  "order_id": "EXACT_ORDER_ID",
  "domain": "exact-domain.com",
  "conclusion": "registrar_confirmed_this_renewal",
  "reference": "Registrar transaction or support case identifier",
  "checked_by": "Responsible operator",
  "checked_at": "CURRENT_ISO_TIMESTAMP"
}
```

Для доказанного невыполнения используется `registrar_confirmed_no_registration_or_renewal`. Не выбирайте его только из-за отсутствия ответа.

```sh
node --env-file=.env bin/operator.mjs record-evidence /private/path/evidence.json
```

Команда принимает только pending-заказ, совпадающий домен и свежую проверку, сохраняет свидетельство и его хеш. Она сама не списывает и не возвращает деньги. После рестарта сверка либо дополнительно проверяет владельца/срок домена, либо начинает возврат по явному подтверждению невыполнения. Повторное/противоречивое свидетельство отвергается. Никогда не редактируйте состояния заказов напрямую ради повторного submit.

## Данные и резервные копии

Сохраняйте вместе базу SQLite, файлы WAL/SHM при их наличии, encryption key и seller signing key. Самый простой согласованный снимок — остановить процесс и копировать каталог. Восстанавливайте одним экземпляром. Возврат к старому снимку может потерять сведения о совершённой операции: до включения продаж потребуется сверка с регистратором и блокчейном. Шифрование не защищает от потери ключа или скомпрометированного работающего процесса.

У покупателя отдельно сохраняются ключ владельца и `DOMAIN_BUYER_DATA_DIR`; они нужны для прав управления и идемпотентного платежа. Смена ключа без процедуры восстановления не переносит домены. Ключ продавца закреплён у покупателей: его замена требует согласованного обновления доверенного каталога.

Публичные котировки очищаются после истечения срока с запасом один час. Контакт удаляется из документа заказа после delivered/refunded/cancelled, но остаётся у регистратора; неоплаченные и спорные заказы, аудит и платёжные сведения пока сохраняются. Автоматическая политика сроков хранения, стирание резервных копий, удаление orphan contacts и восстановление ключа владельца относятся к операционным процедурам, а не к реализованному API.
