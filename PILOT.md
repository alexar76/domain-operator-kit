# На ком проверяем продукт

**Для быстрого тестирования используем [Porkbun Sandbox](PORKBUN.md); Openprovider Sandbox тоже проверен. Первый покупатель — наш агент через MCP. Первый реальный кейс — домен для собственного проекта на Vercel.** Внешних клиентов подключаем после проверки выдачи, прав и восстановления на своих заказах.

Sandbox-пилоты обоих регистраторов выполнены 19 октября 2026: котировки, регистрация, восстановление потерянного ответа, изоляция владельца, DNS, продление и MCP-чтение. Реальные платежи и настоящий проект Vercel пока не проверены. [Текущие результаты](VALIDATION.md).

## 1. Поставщик: Openprovider Sandbox

Уже реализованный адаптер делает Openprovider первым техническим кандидатом. Для sandbox нужен [отдельный аккаунт](https://cp.sandbox.openprovider.nl/signup) и включённый API-доступ. Sandbox имитирует операции без покупки реальных доменов. По [документации Openprovider](https://support.openprovider.eu/hc/en-us/articles/8095671860114-Sandbox-Testing-Environment) трансферы там недоступны, а поддержка TLD зависит от тестовой среды реестра.

| Проверка | Что считаем результатом |
|---|---|
| Цена и доступность | Ответ реального sandbox API, USD, обычное имя, правильный срок и фиксированная наценка |
| Контакт | Создан handle именно переданного владельца |
| Регистрация | В кабинете виден домен с правильным владельцем, сроком и autorenew off |
| Повтор заказа | Повторный вызов и перезапуск не создают вторую регистрацию |
| DNS | Считывание и изменение нужных записей; посторонние MX/TXT сохраняются |
| Продление | Подтверждена конкретная операция, срок вырос на ожидаемый период |
| Потерянный ответ | Заказ восстанавливается по данным регистратора или остаётся честно pending |

Используем `DOMAIN_MODE=sandbox`, `DOMAIN_PROVIDER=openprovider`. Платежи в этом режиме имитируются. Поддержку конкретной зоны проверяем в аккаунте; `.com` не считается гарантированно доступной в sandbox только потому, что она есть в коде.

## 2. Покупатель: наш агент

Сначала запускаем stdio MCP-клиент в собственной агентной среде. Конкретное приложение выбирается по поддержке MCP; одинаковый сценарий должен проходить в выбранном клиенте без ручной подмены ответа.

Задача агенту: найти цену заданного имени, купить в пределах разрешённого бюджета, дождаться подтверждения, прочитать DNS и подключить домен к заранее заданному проекту. Отдельно проверяем, что агент не создаёт новый заказ при pending, не меняет владельца и не обходит лимит расходов.

Автоматический тест MCP уже проверяет транспорт и вызовы. Он не является проверкой интерфейса конкретного установленного приложения.

## 3. Контролируемая настоящая покупка

После sandbox используем **один домен, который действительно нужен нам**, и отдельный тестовый проект Vercel. Точное имя, владелец и верхняя цена определяются до запуска. Код не содержит домена, который нужно купить автоматически.

Понадобятся production-аккаунт регистратора с балансом, выделенный кошелёк покупателя, CDP, кошелёк возвратов с резервом и доступ к нашему проекту Vercel. Ограничиваем покупателя суммой одного согласованного заказа. Условия регистратора и подтверждение email относятся к реальному владельцу.

Успех фиксируем по независимым признакам:

1. Ровно один платёж и один заказ у регистратора.
2. Домен зарегистрирован на правильный контакт, дата истечения корректна.
3. Наш агент имеет доступ к управлению, другой ключ его не получает.
4. Домен прикреплён к нашему проекту; публичный DNS указывает на рекомендованные Vercel значения.
5. `https://домен` действительно открывает ожидаемое приложение с действительным сертификатом.
6. После рестарта повтор заказа возвращает тот же результат, без новой покупки.

Sandbox не подтверждает публичное DNS-разрешение и выпуск HTTPS-сертификата. Статус Vercel API тоже не заменяет проверку сайта. Реальный возврат проверяется отдельно контролируемым сценарием подтверждённой невыдачи; успешную регистрацию нельзя объявлять неудачной ради теста возврата.

## 4. Второй независимый поставщик

Первый партнёр — действующий доменный реселлер со своим аккаунтом регистратора, API, закупочными ценами и поддержкой. Он реализует [HTTP supplier contract](SUPPLIERS.md) и проходит те же сценарии. Наличие работающего локального HTTP-симулятора доказывает переносимость интерфейса, но не подключение второго коммерческого провайдера.

Проверяем, что партнёр может подключиться без изменения клиентских capabilities, использовать свои ключи и цену, подтвердить конкретную регистрацию и восстановить потерянный ответ. Коммерческие условия и возможность реселлинга уточняются с выбранным поставщиком до продаж.

## Что записываем после каждого этапа

Сохраняем версию кода, дату, среду, обезличенные ID заказа/операции, результат и найденные ограничения. Ключи, контакты, платёжные авторизации и коды трансфера в GitHub не попадают. Обновляем `VALIDATION.md` только по фактически проведённым испытаниям.

## Повторяемый sandbox-пилот

Команда ниже создаёт один тестовый домен `.com` и тестовый контакт, записывает DNS, продлевает на год и проверяет восстановление после потери ответа. Используется только жёстко заданный API Openprovider Sandbox и симуляция платежей. Контакт вымышленный и предназначен исключительно для sandbox. Домен сохраняется в sandbox для дальнейших проверок.

```sh
export DOMAIN_MODE=sandbox
export DOMAIN_SANDBOX_PILOT=1
export OPENPROVIDER_USERNAME_FILE="$HOME/.config/domain-kit/sandbox/username"
export OPENPROVIDER_PASSWORD_FILE="$HOME/.config/domain-kit/sandbox/password"
npm run sandbox:pilot
```

Состояние, ключи владельца/продавца и зашифрованная база находятся в игнорируемой Git папке `data/sandbox-pilot/`. Повторный запуск использует тот же домен и те же заказы: регистрация и продление не отправляются повторно. DNS-записи повторно приводятся к тестовым значениям. Не удаляйте состояние незавершённого запуска. При неопределённом результате скрипт останавливается, сохраняя заказ для сверки. Путь можно задать через `DOMAIN_PILOT_DIR`; новый путь создаст отдельный пилот и новый тестовый домен.

При аварийном завершении может остаться `pilot.lock`: перед удалением убедитесь, что процесс с записанным PID завершён. Скрипт не запускает автоматическое удаление доменов или повтор неизвестной операции.

MCP-проверка запускает реальный stdio-процесс `domain-rails` и читает статус, владельцу доступную информацию и DNS зарегистрированного sandbox-домена. Она не является проверкой UI Cursor/Codex. Покупка в пилоте проходит через подписанный HTTP-клиент. Публичный DNS, сертификат HTTPS и Vercel требуют отдельного production-пилота.
