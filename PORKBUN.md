# Porkbun Sandbox: быстрый полный пилот

Второй встроенный адаптер `domain-kit`. Использует те же capabilities, HTTP-клиент и MCP, что Openprovider. Поддерживает `.com`, `.net`, `.org`: котировка, регистрация, продление, сведения о домене и DNS. Код трансфера не объявляется поддержанным.

**Сейчас разрешён только sandbox.** Адаптер отклоняет `live` и production-ключи до запросов, подтверждает `sandbox: true` в ответах. Тестовые операции идут в изолированное хранилище Porkbun, без реальной регистрации, публикации DNS и оплаты. Условия production-реселлинга и проверки владельца ещё не подтверждены.

## Запуск

Новый тестовый аккаунт можно получить автоматически без регистрации в кабинете. Официальный `POST /apikey/request` с `sandbox: true` возвращает пару ключей для отдельного аккаунта с $1000 виртуального баланса. Скрипт сохраняет оба ключа в приватные файлы, не печатает их и не перезаписывает существующий каталог.

```sh
export DOMAIN_MODE=sandbox
export DOMAIN_SANDBOX_PILOT=1
# Только при первой настройке. Если каталог уже существует — пропустить:
npm run sandbox:porkbun:init

export PORKBUN_API_KEY_FILE="$HOME/.config/domain-kit/porkbun/temporary-sandbox/api-key"
export PORKBUN_SECRET_KEY_FILE="$HOME/.config/domain-kit/porkbun/temporary-sandbox/secret-key"
npm run sandbox:porkbun
```

Уже созданная пара работает: повторно выполнять `init` для каждого пилота не нужно. Для другого расположения ключей задайте `PORKBUN_SANDBOX_KEY_DIR` при `init` и соответствующие пути при запуске. Сохраняется именно пара `pk1_sb_…` + `sk1_sb_…`; ручное копирование из кабинета не требуется.

Пилот хранит домен, исходные запросы, ключи подписи и зашифрованную базу в игнорируемом `data/porkbun-pilot/`. Повтор использует те же заказы. Не удаляйте каталог, пока есть неопределённые операции. `DOMAIN_PILOT_DIR` задаёт другой пилот с отдельным состоянием. Оставшийся после аварии `pilot.lock` удаляют только после проверки, что записанный PID завершён.

Для постоянного продавца:

```sh
export DOMAIN_MODE=sandbox
export DOMAIN_PROVIDER=porkbun
export DOMAIN_DATA_DIR=./data/porkbun-server
# PORKBUN_API_KEY_FILE и PORKBUN_SECRET_KEY_FILE — как выше.
npm start
```

Платёж покупателя в sandbox имитируется. Покупки у Porkbun используют виртуальный предоплаченный баланс; адаптер не инициирует пополнение, оплату картой или x402-платёж регистратору. Фиксированная наценка задаётся обычным `DOMAIN_MARKUP_USD`.

## Что проверяет пилот

- Подписанная котировка и регистрация через HTTP capabilities.
- Потеря успешного ответа регистрации, перезапуск и получение той же квитанции Porkbun.
- Запись контактов покупателя, чтение владельца, отключение автопродления; отказ чужому ключу.
- A/TXT-записи, сохранение посторонних наборов, отсутствие записи при неизменном DNS.
- Потеря успешного ответа создания DNS, перезапуск и восстановление без дубликата.
- Продление, потеря его ответа, повтор с тем же ключом; ровно одно увеличение срока на год.
- Реальный stdio MCP-процесс: `status`, `info`, `dnsGet`.

Это проверка автоматизированного транспорта, не UI-сессия Cursor/Codex. Публичный DNS, TLS, Vercel и реальные платежи в sandbox проверить нельзя.

## Восстановление и ограничения

Каждой записи назначается UUID `Idempotency-Key`, который вместе с хешем запроса и временем сохраняется в зашифрованной SQLite **до отправки**. Porkbun обещает повтор исходного ответа в течение 24 часов; kit повторяет неизвестную запись только в пределах **23 часов** с запасом. Успешные квитанции сохраняются локально, повторные вызовы их не покупают заново. После истечения окна или движения часов назад неизвестный результат остаётся pending с `porkbun_replay_window_expired`: оператор сверяет журнал поставщика. Новый ключ или новый заказ для обхода этого состояния недопустим.

Регистрация Porkbun сначала использует контакты аккаунта. Адаптер затем выключает автопродление, присваивает контакт покупателя и независимо читает эти данные. До подтверждения всех шагов заказ не получает `delivered`. Если контакт изменён извне, управление блокируется. Адаптер консервативно возвращает `verify_registrant_email`: чтение метаданных не доказывает прохождение email-проверки. Настройки аккаунта целиком не меняются.

Для DNS сохраняется последовательность изменений по ID записей. Незавершённый план возобновляется только с исходными `revision` и `records`; другая правка получает `porkbun_dns_reconciliation_required`. Минимальный TTL — 600 секунд. DNS API не имеет атомарного compare-and-swap: внешние параллельные изменения нужно исключить. После неизвестного исхода за пределами окна или внешнего изменения оператор сверяет фактическую зону и журнал перед исправлением сохранённого плана. Не удаляйте журнал вслепую.

База привязывается к отпечатку API-ключа, чтобы смена аккаунта не перенесла чужие квитанции в новую среду. Для другого ключа нужен отдельный каталог; ротация с миграцией состояния пока не реализована. Один процесс на одну базу.

Production-пилот должен отдельно подтвердить правила аккаунта/реселлинга, присвоение контактов и письма владельцу, отключение автопродления, расчёты и ограничения продления. Документация указывает запрет продления в первые 30 дней после регистрации/продления; тестовый sandbox позволяет немедленное продление. Поэтому его успех не снимает production-ограничение.
